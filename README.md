# polymarket-whale-tracker

Телеграм-сповіщення про **великі позиції китів** на Polymarket.

Бот запускається за розкладом (GitHub Actions, кожні 5 хв) і надсилає сигнал,
коли трейдер набирає позицію на суму **≥ `MIN_AMOUNT`** ($1M за замовчуванням) —
навіть якщо він робить це не однією угодою, а **кількома дрібнішими** (напр.
5×$200k протягом години).

## Як це працює

- Просить у Polymarket Data API лише **угоди-кандидати**: купівлі (BUY) з сумою
  **≥ `COMPONENT_MIN`** ($100k). Таких небагато — вони завжди влазять у ліміт API.
- Групує їх по **(гаманець + конкретний результат ринку)** і **сумує** за ковзне
  вікно **`AGG_WINDOW_MINUTES`** (60 хв).
- Коли сума позиції ≥ `MIN_AMOUNT` — шле одне сповіщення. Повторний сигнал по
  тій самій позиції — лише якщо вона зросла у `ESCALATE_FACTOR` разів (деф. 2×,
  «кит збільшив позицію»); нова серія починається, коли позиція повністю
  вийшла з вікна (тобто кит повернувся у той самий ринок після паузи).
- Одна велика угода теж спрацьовує (це позиція з однієї угоди).
- Так само ловить і **вихід** кита: продажі (SELL) рахуються окремою позицією
  й приходять окремим сигналом («кит скидає позицію»). Вимикається
  `TRACK_SELLS=0`.
- За один запуск добирає лише нові угоди з моменту минулого запуску, а 60-хв суму
  тримає у стані (`last_check.json`) між запусками — тож ліміт API не є проблемою
  навіть у пікові періоди. Пропуски/затримки запусків GitHub наздоганяються.

## Налаштування

**Secrets** (Settings → Secrets and variables → Actions → Secrets):

| Ключ | Опис |
|---|---|
| `TELEGRAM_TOKEN` | токен Telegram-бота |
| `TELEGRAM_CHAT_ID` | ID чату/каналу для сповіщень |
| `MIN_AMOUNT` | поріг сигналу, $ (напр. `1000000`) |

Залежностей у Python немає — бот працює на стандартній бібліотеці.

**Variables** (необов'язкові; порожні = дефолти):

| Ключ | Дефолт | Опис |
|---|---|---|
| `COMPONENT_MIN` | `100000` | мінімальна окрема угода, яку рахуємо як частину позиції |
| `AGG_WINDOW_MINUTES` | `60` | вікно агрегації угод одного трейдера |
| `ESCALATE_FACTOR` | `2` | повторний сигнал по тій самій позиції — коли зросла у стільки разів |
| `STATE_HEARTBEAT_MINUTES` | `30` | як часто зберігати стан у репо, якщо нічого не сталося |
| `MIN_RUN_INTERVAL_SECONDS` | `45` | коротший інтервал = дублюючий запуск, він одразу виходить |
| `WINDOW_LAG_SECONDS` | `5` | межа вікна відстає від «зараз» — щоб не губити угоди на стику секунди |
| `RESCAN_OVERLAP_SECONDS` | `180` | наскільки перечитувати назад — страховка від затримки індексації API |
| `FETCH_BUDGET_SECONDS` | `90` | ліміт часу на вибірку, щоб не потрапити під таймаут джоби |
| `TRACK_SELLS` | `1` | `0` — не сигналити про великі продажі |
| `DAILY_DIGEST` | `1` | `0` — вимкнути щоденний підсумок |
| `DAILY_DIGEST_HOUR` | `9` | о котрій годині **UTC** надсилати підсумок |
| `DIGEST_TOP` | `3` | скільки найбільших угод показувати у підсумку |
| `ENABLE_COMMANDS` | `1` | `0` — не відповідати на команди в Telegram |

## Команди в Telegram

Напишіть боту в чат:

| Команда | Що показує |
|---|---|
| `/status` | чи живий бот, налаштування, останній сигнал, що він бачить зараз |
| `/top` | топ позицій у поточному вікні — **навіть тих, що не дотягли до порогу** |
| `/help` | довідка |

Відповідь приходить під час найближчого запуску (до 5 хв): окремого процесу
для миттєвого опитування тут немає.

## Щоденний підсумок

Раз на добу (о `DAILY_DIGEST_HOUR` UTC) приходить зведення за останні 24 години:
**топ-3 найбільші угоди** — сума, сторона, ціна, подія, результат, трейдер,
посилання на трейд і на подію — плюс рядок «усього угод ≥ `COMPONENT_MIN` за
добу та їхній обсяг».

Це заразом показує, що бот живий: на порозі $1M спокійні тижні без жодного
сигналу цілком нормальні, і без підсумку **тиша на ринку виглядає як зламаний
бот**.

## Запуск за розкладом

Основний тригер — **зовнішній планувальник** (cron-job.org) через
`workflow_dispatch` кожні 5 хв. У самому workflow залишено **рідкісний
страхувальний розклад** (`:07` і `:37` щогодини) на випадок, якщо зовнішній
планувальник замовкне.

Важливо не повертати в workflow розклад `*/5`: тоді обидва джерела стріляють
одночасно, запуски стають у чергу concurrency-групи, і при будь-якій затримці
GitHub вони каскадом скасовуються («No jobs were run») або падають зі
«Startup failure».

## Що містить сповіщення

Назву події, ставку (Yes/No) і ціну, суму позиції та кількість угод, трейдера
(з посиланням на профіль), розкладку угод з посиланням на кожну транзакцію та
посилання на подію.

Біля кожної угоди видно, як її виконано: **⚡ маркет** (ринковий ордер) або
**📘 лімітка**. Плюс рядок-підсумок, скільки з позиції набрано кожним способом.
Тип визначається порівнянням з вибіркою `takerOnly=true` (у відповіді API поля
maker/taker немає); якщо той запит не вдався, сповіщення приходить без міток.

## Скільки сигналів очікувати

Заміри на живих даних за 27.7 доби (реплей цього ж алгоритму по історії API):

| Поріг сигналу | Сигналів за тиждень (спокійний ринок) |
|---|---|
| $1,000,000 | 1 |
| $750,000 | 4 |
| $500,000 | 7 |
| $300,000 | 16 |
| $200,000 | 35 |

Потік дуже нерівномірний: за 27.7 доби всього 36 сигналів, і 34 з них — у
пікові дні (плей-оф ЧС, 07–19.07). У спокійний період на порозі $1M
нормально не отримати **жодного сигналу за тиждень** — це ринок, а не збій.
Довше вікно агрегації допомагає слабо (60 хв → 1, 24 год → 3 за тиждень);
на кількість сигналів впливає майже виключно поріг.

## Тести

`python test_tracker.py` — 37 сценаріїв: дроблення позиції, накопичення через
кілька запусків, ескалація, багатоваріантні ринки (Spain/Over/Under),
продажі, часткові виконання, дублі, межі вікна, наздоганяння після простою,
міграція старого стану, помилки Telegram, команди, щоденний підсумок.
Мережі не торкаються.

## Обмеження

- Дуже дрібне дроблення (нижче `COMPONENT_MIN`) не враховується.
- Накопичення, повільніше за вікно агрегації, побачимо лише частково.
- «Миттєвих» сповіщень немає: розклад — кожні 5 хв (плюс можливі затримки GitHub).
- Обмін через split/merge/redeem (без угоди в книзі) у `/trades` не потрапляє.
